# P0-T06 断点笔记

日期：2026-09-06

## 学习目标

把厂方 SSE/JSON 差分隔在适配器内；Runner 只看见 `ModelStreamEvent`（`text_delta` / `tool_call` / `usage`）。P0 以 OpenAI 官方 `chat.completions` 流式形态为准，不抽象「万能解析器」。

## 我亲手验证过的行为

- Mock HTTP 服务器返回 `text/event-stream`：`data: {...}` content delta → 适配器产出 `text_delta`（`Hello` + ` world`）。
- 同一流末尾带 `usage` → 产出 `usage`（`prompt_tokens` / `completion_tokens`）。
- `tool_calls` 按 `index` 分片到达：`id`/`name` 在首片，`arguments` 字符串后续拼接，`finish_reason: tool_calls` 时 `JSON.parse` 成一个完整 `tool_call`。
- 请求打到 `{baseUrl}/chat/completions`，`Authorization: Bearer`，body 含 `stream: true`；`ToolDefinition` 映射为 OpenAI `tools[].function`。

## 自问

- **`baseUrl` 为什么常要带 `/v1`？** OpenAI 把协议版本放在路径前缀，完整 URL 是 `{origin}/v1/chat/completions`。兼容网关（DeepSeek、OpenRouter、本地 llama.cpp 等）也照这个路径挂载，所以 `baseUrl` 写成 `https://api.openai.com/v1`，适配器只拼 `/chat/completions`，而不是把 `/v1` 写死在代码里。
- **tool_calls 流式是「分片到达」还是「一次性」？聚合策略是什么？** 官方形态是分片：同一 `index` 上多次 `delta.tool_calls`，`function.arguments` 是 JSON **字符串碎片**。策略：按 `index` 累加 `id`/`name`/`arguments`，在 `finish_reason` 或流结束时 parse 一次再 yield `tool_call`。部分网关会一次性给完整 `arguments`——同一套拼接逻辑也能吃（等于只有一片）。

## 各家差异（记下来，不立刻抽象）

- OpenAI：`index` + arguments 字符串碎片（本适配器只认这个）。
- 有的网关：最后一个 chunk 才给完整 `tool_calls`，中间没有碎片。
- 有的网关：`arguments` 已是对象而不是字符串（P0 不处理）。
- Anthropic 是另一套 `content_block_delta`，不属于本 Provider。

## 还不懂的点

- `stream_options.include_usage` 各家是否默认带 usage；P0 见到 `usage` 就转，没有也不补。
- 并行多个 `tool_calls`（index 0/1）在真实网关上的交错方式，目前按 index 分桶，尚未用真实 key 打过。
