# P0-T09 断点笔记

日期：2026-09-06

## 学习目标

Agent UX 的核心是事件流：模型增量变成 `message_delta`，工具进出变成 `tool_start` / `tool_end`。停止不是“再发一条取消消息给模型”，而是对本 run 的 `AbortSignal`。P0 权限默认 auto-allow 已注册工具。

## 我亲手验证过的行为

- 注入 mock `ModelPort` 后，WS `/ws` 发送 `{ type: "run", sessionId, content }`：先收到带 `runId` / `sessionId` / `traceId` 的 `run_start`，再逐条 `message_delta`（`hel` + `lo`），最后 `run_end.reason = completed`。
- 同一 session 随后 `GET /sessions/:id` 能看到持久化的 user + assistant（`hello`）。
- 慢流 mock 在第一片 `tick` 后 `POST /runs/:runId/stop`：`run_end.reason = stopped`，后续 `should-not-appear` 不再到达。
- `assembleRuntime`：`apiKeyEnv` → `env`；缺 key 抛错；注入 model 时不读 key。生产路径用 `createOpenAICompatibleModel`。
- 映射时显式拷贝 `runId`、`toolCallId`，避免结构展开漏字段。

装配顺序：config → db → sessionStore / tracePort / RunHub → `@fastify/websocket` → routes。每次 run 按当前 config 再 assemble（`PUT /config` 影响下一轮）。

## 自问

- **map 事件时哪些字段绝对不能丢？** `runId`（UI 用来 stop / 对齐时间线）和 `toolCallId`（`tool_start`/`tool_end` 配对）。`sessionId`/`traceId` 在 `run_start` 同样不能丢。
- **停止 = AbortSignal 为什么够？** Runner 在模型流、工具执行、权限等待里都看 `signal`。Hub 按 `runId` 持有 `AbortController`，HTTP stop 只 `abort()`，不另开一条“取消协议”。
- **config 热更新重建什么？** 本 Task 选择「下一轮 run 再 assemble」，不热替换进行中的 Model/Tools。进行中的 run 仍用启动时那套依赖，直到 `run_end`。

## 还不懂的点

- 公司网关若不是严格 OpenAI SSE，真实流可能和 mock 不一致；本轮 CI 只用 mock，没有贴原始响应片段。
- `permission_response` 已留接口，P0 未接线；`ask_all` 时 WS 往返还没做。
- 同一条 WS 上并发多个 run 时，客户端如何把 stop 和事件按 `runId` 对齐（协议已支持，UI 未做）。
